# V2 第二阶段架构

本地单企业、单SKU订单、USD。V1只读；业务空间 business 与 Synthetic / 模拟演示空间 demo 全链路隔离。无云、无付费API、无AI模型或身份认证。

“第二阶段独立模拟演示”使用当前 runtime/phase2_demo/ 下的独立数据库（workspace仍为demo），防止第一阶段同SKU的商品或库存演示记录与14天场景冲突。原第一阶段模拟和业务空间不重置；筛选控件与检测结果按数据库目录＋空间命名，不混用Session State。

## 模块与调用关系

`app.py` 保留第一阶段数据工作台，使用 sidebar 导航调用 `phase2_ui.py`。界面只筛选、格式化、显示和提交表单；业务公式、规则和写事务不放在页面。

- `service.py`：原文件、批次、行指纹幂等、V1质检、质量审核、事务日志。`Store.metrics` 委托统一指标中心返回第一阶段兼容契约。
- `metrics.py / MetricCenter`：同一个有效版本快照，生成订单、退款、广告、库存事实。所有第一阶段指标、第二阶段看板、图表、指标导出及预警调用该服务。
- `revisions.py`：非业务键字段的申请、凭证引用、审批、基版本哈希、有效版本链。原始 records 永不更新。
- `alerts.py`：统一规则接口、同长度周期、数据不足跳过、版本快照、稳定预警唯一键、状态操作审计。
- `migrate.py` 和 `migrations/002_phase2.sql`：可重复、校验和锁定的增量迁移；有业务记录的旧库迁移前自动 SQLite backup。

有效数据路径：不可变 records → 依次应用已批准修订 → 原V1规则重新质检 → 读取有效质量审核状态 → 隔离/利润隔离 → 统一事实快照 → 指标/预警/明细/导出。

## 数据库

保留五张第一阶段表；新增：

|表|用途|
|---|---|
|schema_migrations|版本、SQL SHA256、执行时间、一致性备份路径|
|alert_rules|当前规则配置，空间+类型唯一；当前版本号|
|alert_rule_versions|追加每个规则版本、阈值、窗口、操作人、说明|
|alerts|规则ID/版本、对象、周期、指标、阈值快照、证据、状态、检测时间|
|alert_actions|追加原/新处理状态、说明、操作人、时间|
|alert_detections|每次实际运行的指标和来源证据；重新计算不会覆盖最初检测证据|
|record_revisions|原始记录引用、基哈希、原值、新值、原因、凭证、申请人、状态、生效时间、关联异常|
|revision_reviews|追加批准/驳回、说明、操作人、时间|

必要索引覆盖工作空间预警队列、有效修订和业务唯一键。原记录、旧质量审核、操作日志、新审批/处理/规则/检测历史有追加或不可变约束。写操作使用 BEGIN IMMEDIATE；审批、质检重评、审计在同一事务内。指标快照用读取事务避免半次导入。

## 迁移与安全

Store启动先检查原DDL，再自动应用第二阶段迁移。002增加业务表，003增加持续预警与历史周期检索索引；没有改写已执行的002。迁移SQL只增加表、索引与保护触发器，不删除、重命名或替换旧表。相同版本相同哈希跳过；哈希变化则停止，必须新增迁移文件。旧库已有记录时在 runtime/backups/ 保存每步一致性备份，并在 schema_migrations 记录路径。备份、SQLite、上传文件均被 v2/.gitignore 排除。

SQLite备份覆盖数据库；原上传文件目录独立保留，完整系统备份应停止应用后复制整个 runtime。极端断电文件落盘与数据库事务仍不是同一原子事务，原第一阶段限制不变。

## 导航兼容

六个导航分组对应九项功能：数据运营工作台中的导入、质量、异常审核、批次与日志四个页签；经营总览、经营监控、智能预警、数据修订、规则配置。第一阶段四个页签、按钮和操作语义保留。8502不变。部署/更新后实际重启8502，旧模块版本契约也保留防护。

后台接口契约API版本3不是产品第三阶段；用于新增成本来源字段的热更新保护。界面检测旧Store时按依赖顺序重新加载指标/修订/预警/界面模块，避免新界面遇到驻留旧模块的KeyError；交付仍实际重启服务，不仅依赖热更新。

## 限制

小批量单机数据，按当前有效版本全量重评，不是增量数据仓库。静态成本修订对当前视图的历史订单重算，不代表成本价格随日期变动；没有成本生效日模型。没有企业认证、电子签名、角色权限、外部采集、计划任务或通知。数据库操作者拥有本机文件权限，审计不能抵抗有管理员权限的人直接篡改数据库。
