## 结论与根因

**在隔离空数据库中，提交前版本和修订后版本都未复现“正常上传后仅重复上传，9月销售35变70”。** 两版的完整指标快照在重复前后均相同，没有证据支持文件级去重或聚合存在该数值 Bug。本次没有更改去重、隔离或 V1 金额公式。

只读检查用户现用 `v2/runtime/monitor.sqlite`，找到现值70的确定来源：`errors.csv` 中的 `UNKNOWN_SKU` 是一笔不同订单，另计35收入，因 SKU999 成本未知而隔离利润。与正常订单 DEMO001 的35相加得到70；9月成本已知样本仍只有 DEMO001，所以贡献仍10。

原界面的三个演示按钮共享持久化 demo 空间，却未明确展示累计范围和逐笔来源；正常场景的固定预期文本易让人将整个空间视为单个场景。这是本次修订的界面解释与可追溯性问题。

## 去重、样本、SQL/Pandas、界面执行检查

- 文件去重使用空间＋SHA-256＋导入类型；duplicate 分支在插入记录、refresh、计算之前返回。只追加重复批次及日志，业务 records 和 anomalies 完全不变。
- 行指纹唯一约束防止跨文件重复；重新生成 ZIP 元数据不同的 Excel、六表 CSV、重排字段、并发重复上传均检查。不同内容相同业务键继续全部隔离，未更改该规则。
- 聚合读取 records，未按 batches 联接复制业务行；收入样本和利润样本按 V1 区分。未知SKU的35进入收入，不进入成本已知利润样本。
- `audit_duplicate.py` 从原始记录及审核标记分别执行独立 SQLite SQL 与 Pandas/Decimal 筛选和汇总。正常样本及含错误样本的订单数、收入、商品成本、物流、佣金、退款、广告、毛利、贡献逐项一致。
- app.py 没有 `st.cache_data` 或 `st.cache_resource` 缓存指标；每次 rerun 从 SQLite 计算。Session State 仅用于瞬时导入提示、审核提示及控件状态，不追加订单或金额。按钮事件调用一次 ingest 后 rerun；连续重复点击另有并发与 UI 回归测试。
